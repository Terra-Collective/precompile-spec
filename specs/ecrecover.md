## Abstract

Add functionality to efficiently perform ECDSA public key recovery over the secp256k1 elliptic curve (also known as Koblitz curve). This precompile enables native support for public key recovery of any hash generated by secp256k1 curve (e.g. Ethereum signatures).

## Motivation

The secp256k1 elliptic curve is a widely supported curve across blockchains. Adding native support for secp256k1 public key recovery to Terra via the `x/crypto` module to be used through a custom query instead of current `secp256k1_recover_pubkey` CosmWasm function, which is not particularly suitable or optimized for Ethereum enables light clients, bridges, and many important use cases with smart contracts on Terra, thanks to both architectural compatibility with Terra's future precompiles and predictable gas costs at the L1 level.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119 and RFC 8174.

### Precompile

We introduce `ECRECOVER` a precompile at the `x/crypto` module which performs ECDSA public key recovery over the secp256k1 curve with a gas cost of `78000` gas.

It SHALL be implemented by adding a gRPC query router to the `x/crypto` module. Smart contracts MAY interact using `deps.querier`.

| Property | Value |
| --- | --- |
| Path | `/terra.crypto.v1beta1.Query/Ecrecover` |
| Curve | secp256k1 |
| Input | `hash ‖ v ‖ r ‖ s`, 4 × 32 bytes, 128 bytes expected, any length accepted |
| Output | 32 bytes (12 zero bytes ‖ address) on success, 0 bytes on failure |
| Gas | 78000, fixed |

### Curve Parameters

ECRECOVER works on which is fully defined by the following set of parameters:

``` text
Base field modulus = p = 0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFEFFFFFC2F
Curve equation: y^2 = x^3 + ax + b (mod p)
Curve coefficient a = 0x0
Curve coefficient b = 0x7
Base point G:
  Gx = 0x79BE667EF9DCBBAC55A06295CE870B07029BFCDB2DCE28D959F2815B16F81798
  Gy = 0x483ADA7726A3C4655DA4FBFC0E1108A8FD17B448A68554199C47D08FFB10D4B8
Subgroup order = n = 0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFEBAAEDCE6AF48A03BBFD25E8CD0364141
```

These parameters are standardized in SEC 2: Recommended Elliptic Curve Domain Parameters[^1].

### Fields and Groups

ECRECOVER computes in two finite fields of the same curve, `Fp` for point coordinates and `Fn` for signature scalars.

The field `Fp` is the finite field of size `p`, with elements represented as integers between `0` and `p-1` (both inclusive). The coordinates of `R` and of the recovered key `Q` live here.

The field `Fn` is the integers modulo the prime `n`. The values `r`, `s`, the message hash reduced mod `n`, and `r^(-1)` live here.

The group `G` is the set of `Fp` pairs `(x, y)` that satisfy the curve equation `y^2 = x^3 + 7` (mod `p`), together with the point at infinity. It is cyclic of prime order `n` and generated by the base point `G`.

No point appears in the input or the output, so the precompile fixes no encoding for the point at infinity. It occurs only inside the algorithm, as a failure case.

### Points and Encoding

Every input is a 32 byte big-endian word and the precompile never takes or returns a curve point.

| Item | Encoding | Rule |
| --- | --- | --- |
| `h` | 32 bytes, big-endian | Any value is accepted. Implementation reads it as an integer and reduces it mod `n`. |
| `v` | 32 bytes, big-endian | Must equal 27 or 28 as a full 256 bit integer. |
| `r`, `s` | 32 bytes each, big-endian | Each must satisfy `0 < value < n`. |
| `Q` (internal) | 65 bytes: `0x04 ‖ X ‖ Y` (uncompressed) | Never returned. The `0x04` prefix byte is dropped before hashing. |
| Output | 32 bytes: 12 zero bytes ‖ 20-byte address | Last 20 bytes of `keccak256(X ‖ Y)`. |

### Behavior on Invalid Inputs

On any input that cannot yield a signer, the precompile returns 0 bytes and the call still succeeds. Implementation SHALL be returns `nil, nil` on every failure path, so nothing reverts and the caller sees zero bytes of return data.

Input length is not an invalid input condition. Input shorter than 128 bytes is right padded with zeros, and bytes beyond offset 127 of a longer input are never read.

### Input

ECRECOVER reads 128 bytes of input, interpreted as the byte concatenation of:

| Offset | Size | Field |
| --- | --- | --- |
| 0 | 32 bytes | `h` |
| 32 | 32 bytes | `v` |
| 64 | 32 bytes | `r` |
| 96 | 32 bytes | `s` |

Any input length is accepted. Input shorter than 128 bytes is right-padded with zero bytes. A missing tail reads as zero bytes, so a 127 byte input is the same as the 128 byte input whose last byte is `0x00`. Input longer than 128 bytes is not cut. The padding step returns it unchanged, and bytes at offset 128 and beyond are never read.

### Output

Output is 32 bytes on successful recovery and 0 bytes on failure, `0x000000000000000000000000` followed by the 20-byte signer address for a recoverable signature and empty for anything else.

### Input Validation

The precompile MUST run the following three checks before any curve arithmetic and return empty output if any check fails (index is assumed to be zero based):

1. `v` word: bytes 32 to 62 MUST all be zero.
2. `v` value: `input[63] - 27`, computed in mod 256, MUST be 0 or 1. Equivalently, `input[63]` is 27 or 28.
3. Signature component bounds: both `r` and s MUST satisfy `0 < r < n and 0 < s < n`.

No other value is checked. Any 32 byte hash is accepted, and there is no public key input to validate.

### Signature Recovery Algorithm

ECRECOVER derives the signer's public key as `Q = r^(-1) * (s*R - z*G)` and returns the address of `Q`. EMPTY is the zero length output.

```text
# Input normalization
input = right_pad(input, 128)            # longer input is kept as is, only bytes 0..127 are read
h = input[0:32]
r = int_be(input[64:96])
s = int_be(input[96:128])
v = (input[63] - 27) mod 256             # byte arithmetic, wraps around

# Input validation (as specified above)
if any_bit_set(input[32:63]):
    return EMPTY
if not (0 < r < n and 0 < s < n):
    return EMPTY
if v not in (0, 1):
    return EMPTY

# Lift the point R = k*G used during signing from its x-coordinate r
# recid = v, so the x-coordinate is r itself (recid 2 and 3, the "r + n" cases, are unreachable)
R = point_with_x(r, y_is_odd = (v == 1))
if R does not exist (r^3 + 7 is not a square mod p):
    return EMPTY

# Recover the public key
z  = int_be(h) mod n
r1 = r^(-1) (mod n)
Q  = (s * r1) * R + (-(z * r1) mod n) * G      # Q = r^(-1) * (s*R - z*G)

# Check for point at infinity
if Q is the point at infinity:
    return EMPTY

# Derive the address
pub  = 0x04 || Q.x || Q.y                 # 65 bytes, uncompressed
addr = keccak256(pub[1:])[12:]            # last 20 bytes
return 0x000000000000000000000000 || addr # 32 bytes
```

### Error Cases

Six conditions return empty output, and none of them reverts or changes the gas charged (index is assumed to be zero based):

1. The upper bytes of the `v` word are not zero.
2. `input[63]` is neither 27 nor 28.
3. `r = 0` or `s = 0`.
4. `r ≥ n` or `s ≥ n`.
5. No curve point has `x` coordinate `r` (`r^3 + 7` is not a square mod `p`).
6. The recovered public key is the point at infinity.

### Gas Burning on Error

The precompile MUST NOT revert on invalid input. Implementation always returns a `nil` error, every failure returns empty output, and the same 78000 gas is consumed as for a successful recovery. The one failure a caller can see is running out of gas when less than 78000 is supplied, implementation settles that before operation.

## Security Considerations

ECRECOVER roughly half of all values of `r` it returns an address even when the signature is garbage, so the caller must compare that address with the signer it expects.

Caller MUST reject the zero bytes.

Signatures are malleable. For a valid `(r, s, v)`, the triple `(r, n - s, 55 - v)` recovers the same address, and the precompile accepts both.

`v` must be 27 or 28. A library that emits 0 or 1, or an `EIP-155` style value, gets empty output until it is normalised.

Length is not enforced. A truncated input is padded on the right and still recovers an unrelated address.

ECRECOVER does not hash the message or bind a domain, chain or nonce; the caller does.
